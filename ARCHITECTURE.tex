\begin{tcolorbox}[title=What is this project?]
A custom secure desktop web browser, codenamed \textbf{PromptGuard}, that uses Artificial Intelligence (AI) to browse the internet on your behalf. The fundamental security challenge: malicious websites can embed hidden instructions (Indirect Prompt Injection) or users can enter hostile prompts (Direct Prompt Injection) to hijack the AI. This project introduces a multi-stage, isolated security architecture that detects and blocks those attacks in real time before instructions can reach the Large Language Model or trigger browser actions. The autonomous agent drives the browser through a purpose-built, typed Chrome DevTools Protocol (CDP) runtime rather than any third-party automation framework, and the chat/agent assistant can be pointed at any of several LLM providers the user configures, not a single fixed vendor.
\end{tcolorbox}

\section{Frontend --- What the User Sees}

The frontend is everything the user interacts with directly. It is built as a desktop application using \textbf{Electron 42.3}, \textbf{React 19.2}, and \textbf{TypeScript 6.0} (a hardened, custom browser shell -- not a fork of an existing browser).

\begin{tcolorbox}[colback=red!6!white,colframe=red!55!black,title=Design change since v2.0]
Earlier iterations of this project drove the browser through \textbf{Stagehand}, a third-party natural-language automation library. Stagehand has since been \textbf{removed entirely} -- it is no longer a dependency, and no code in the repository references it. \subsection{How the Frontend Captures Webpage Content for Scanning}

When you click \textbf{"Scan Page"}, or when the autonomous agent is about to act on a page, PromptGuard captures content across the same \textbf{14 classified channels} in both paths (kept identical on purpose -- see Section~\ref{sec:isolation}):

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{BX}
\toprule
\textbf{Content Channel} & \textbf{What It Captures} \\
\midrule
\textbf{\pth{visible\_text}} & All readable text rendered on the screen. \\
\textbf{\pth{hidden\_text}} & Text hidden with \texttt{display:none}, \texttt{visibility:hidden}, \texttt{opacity:0}, or off-screen. \\
\textbf{\pth{html\_comments}} & Developer comments embedded in page source (\texttt{<!-- injection directive -->}). \\
\textbf{\pth{meta\_tags}} & Page metadata, OpenGraph properties, and search description tags in \texttt{<head>}. \\
\textbf{\pth{input\_values}} & Pre-filled text, placeholders, and current values in form inputs. \\
\textbf{\pth{aria\_text}} & Accessibility labels, descriptions, and ARIA roles. \\
\textbf{\pth{iframe\_content}} & Content loaded within embedded (same-origin) child frames. \\
\textbf{\pth{shadow\_dom\_content}} & Encapsulated components used by modern web frameworks. \\
\textbf{\pth{inline\_javascript}} & Raw script strings and inline JavaScript blocks in the HTML. \\
\textbf{\pth{css\_content}} \newline \textbf{\pth{css\_generated\_content}} & Stylesheet text and generated pseudo-element content (\texttt{::before}, \texttt{::after}). \\
\textbf{\pth{network\_responses}} & Intercepted API responses and HTTP payloads received by the page. \\
\textbf{\pth{websocket\_messages}} & Live real-time bidirectional message frames. \\
\textbf{\pth{service\_worker\_activity}} & Cached background scripts and service worker storage. \\
\bottomrule
\end{tabularx}
\caption{The 14 Content Channels Fed to the Classifier}
\end{table}

The agent's raw security snapshot additionally captures \texttt{external\_javascript}, \texttt{dom\_snapshot\_content}, \texttt{page\_title}, and \texttt{url} (18 fields total), but these four are \textbf{not} passed to the classifier: \texttt{page\_title}/\texttt{url} are metadata used for the scan cache key, \texttt{external\_javascript} is not currently scanned, and \texttt{dom\_snapshot\_content} (the raw \texttt{DOMSnapshot.captureSnapshot} string table) was deliberately excluded after it produced no additional true positives over the other 14 channels while adding pure noise. The semantic \textbf{Accessibility Tree (AXTree)} used to plan and execute agent actions is captured separately from this security snapshot (see Section~\ref{sec:runtime}).

\subsection{Multi-Provider LLM Gateway}
\label{sec:providers}

OpenCode Zen is no longer the sole, hardcoded LLM path. The backend now ships a \textbf{provider manager} and \textbf{gateway factory} so the user can connect any of several LLM vendors -- \textbf{no provider is assumed as a default}; chat and planning simply return a "no provider configured" placeholder until the user activates one.

\begin{table}[H]
\centering
\small
\begin{tabularx}{\textwidth}{CXX}
\toprule
\textbf{Preset ID} & \textbf{Provider} & \textbf{Gateway Implementation} \\
\midrule
\pth{opencode} & OpenCode Zen (\texttt{opencode.ai/zen}) & \pth{OpenAICompatibleGateway} \\
\pth{openai} & OpenAI & \pth{OpenAICompatibleGateway} \\
\pth{nvidia} & NVIDIA NIM & \pth{OpenAICompatibleGateway} \\
\pth{agentrouter} & AgentRouter proxy & \pth{OpenAICompatibleGateway} \\
\pth{cloudflare} & Cloudflare Workers AI & \pth{OpenAICompatibleGateway} \\
\pth{custom} & Any OpenAI-compatible endpoint (vLLM, Ollama, Groq, ...) & \pth{OpenAICompatibleGateway} \\
\pth{anthropic} & Anthropic Claude & \pth{AnthropicGateway} (native \texttt{/v1/messages}) \\
\pth{gemini} & Google Gemini / AI Studio & \pth{GeminiGateway} (native Generative Language API) \\
\bottomrule
\end{tabularx}
\caption{Supported LLM Provider Presets}
\end{table}

Every gateway implements the same three-method interface: \texttt{list\_models()}, \texttt{chat\_completion()}, and \texttt{validate\_key()}, so \texttt{agent\_planner\_service.py} and \texttt{llm\_provider\_manager.chat()} never branch on vendor. Credentials are entered once in \texttt{ProviderSettingsModal.tsx}; \texttt{providerSecureStore.ts} on the Electron side encrypts the API key with OS-level \texttt{safeStorage} (falling back to base64 only when the OS keychain is unavailable), persists it under \texttt{\%APPDATA\%/prompt-defense-browser/provider\_settings.json}, and syncs only the decrypted \emph{active} provider to the backend over \texttt{POST}/\texttt{DELETE /api/v1/providers/active} -- the backend never sees or stores the credentials of an inactive provider.

\section{Browser Runtime --- How the AI Agent Drives the Browser}
\label{sec:runtime}

\subsection{From Stagehand to a Typed CDP Runtime}
Earlier designs drove the browser through Stagehand's natural-language \texttt{act}/\texttt{observe}/\texttt{extract} API. That dependency has been \textbf{fully removed}. The agent now drives registered Electron guest \texttt{<webview>}s through a single main-process \textbf{\texttt{BrowserRuntime}}, exposed to the renderer only through the one typed \texttt{agent:runtime:invoke} IPC bridge. The runtime validates the target session, command name, parameter object, and element handle before dispatching any CDP work, and returns typed \texttt{\{ok, data\}} / \texttt{\{ok: false, error\}} envelopes rather than raw exceptions.

\subsection{Supported Runtime Commands}
The runtime's command map (\texttt{RuntimeCommandMap} in \texttt{runtimeContract.ts}) currently exposes 14 commands: \texttt{describeTarget}, \texttt{extractPageState}, \texttt{captureScreenshot}, \texttt{captureSecuritySnapshot}, \texttt{navigate}, \texttt{click}, \texttt{fill}, \texttt{type}, \texttt{pressKey}, \texttt{scroll}, \texttt{upload}, \texttt{waitForNavigation}, \texttt{waitForDomStable}, and \texttt{setAgentOverlay}. Each browser action is wrapped in \texttt{withVerification}: a before/after signature is captured, the native CDP input is dispatched, and the after-state is compared against an expectation (\texttt{url} for navigation, \texttt{value} for \texttt{fill}, \texttt{change} for \texttt{click}) before the action is acknowledged.

\begin{tcolorbox}[title=Upload is structural, not procedural]
\texttt{DOM.setFileInputFiles} can hand any readable file to a remote site, so its defence is not a permission prompt but the shape of the API itself: the \textbf{planner names only the target field}, never a file path. A native OS file picker, driven by the user, supplies the actual path -- \texttt{UploadParams} has no \texttt{filePaths} field at all. A fully compromised planner can, at worst, cause a file dialog the user cancels.
\end{tcolorbox}

\begin{lstlisting}
                        goal
                         |
                         v
                 Agent Runtime Core (renderer)
                         |
              extractPageState (AXTree)
                         |
        +----------------+----------------+
        |                                 |
  PLANNING PIPELINE                SECURITY PIPELINE
        |                                 |
  State Builder -> semantic state   deep CDP content snapshot (14 channels)
        |                                 |
  POST /api/v1/agent/plan          POST /api/v1/agent/scan-active-page
        |                                 |

        |                                 |
        +----------------+----------------+

                 [ CIRCUIT BREAKER ]

        +----------------+----------------+

        |                       end the task, log it

        |

The two pipelines run \textbf{concurrently} (\texttt{Promise.allSettled}), because neither depends on the other's result and both are on the critical path. This is only safe because of the rule that governs it: \textbf{the planner may produce an action while a scan is in flight, but nothing executes until the security verdict is in.}

\subsection{The Detection Pipeline (Step by Step)}

\begin{lstlisting}
Your Text Arrives (User Prompt OR Extracted Webpage Channels)
  |
  +---> STEP 1: PREPROCESS & SANITIZE
  |     - Normalize Unicode representations (NFKC).
  |     - Strip non-printable control characters.
  |     - Clean whitespace and convert to lowercase.
  |
  +---> STEP 2: SLIDING-WINDOW CHUNKING
  |     - Slices text into 800-character chunks.
  |     - Applies a 100-character overlap between adjacent chunks.
  |     - Guarantees boundary-straddling attacks are never split.
  |
  +---> STEP 3: CLASSIFICATION INFERENCE
  |     - Evaluates each chunk via the Active Rule-Based Detector (or ML model when loaded).
  |     - Generates confidence score and evidence reasons.
  |
  +---> STEP 4: AGGREGATE DECISION
        - If ANY chunk is flagged as malicious -> Input is BLOCKED (allowed: false).
        - If ALL chunks are safe -> Input is ALLOWED (allowed: true).
\end{lstlisting}

Two structural rules apply everywhere in this pipeline. \textbf{Fail closed:} a missing verdict, an unreachable backend, a failed capture, or an empty snapshot all deny execution -- the backend returns HTTP 400 rather than \texttt{allowed: true} for an empty webpage snapshot, because an empty capture is not evidence of safety. \textbf{No re-arming:} once the agent's circuit breaker trips within a task, it stays tripped for that task; a page that flickers between hostile and clean content cannot earn its way back to executing.

\section{Known Limitations \& Design Rationale}

Documented directly in \texttt{docs/AGENT\_ARCHITECTURE.md} so they are not lost as the system evolves:

\begin{itemize}[leftmargin=1.4em]
\item \textbf{Cross-origin iframes are invisible.} \texttt{Accessibility.getFullAXTree} on the page target reaches same-origin subframes but not out-of-process ones. An injection inside a cross-origin iframe appears in \emph{neither} the semantic state nor the security snapshot -- this is the most significant gap in the security story today; closing it needs CDP target auto-attach and a per-target session.
\item \textbf{Detection quality is inherited.} With no trained model present, every path runs on the regex rule-based detector; its false negatives are the system's false negatives.
\item \textbf{The precision rules trade some recall.} An injection phrased without second-person directive language, using only a weak indicator, is deliberately not flagged.
\item \textbf{\texttt{dom\_snapshot\_content} is captured but never scanned} by either pipeline -- its overlap with the 14 scanned channels is near-total, but the noise from scanning it was not.
\item \textbf{Scan-then-act is not atomic.} A page could mutate between the snapshot and the action landing; the content hash catches this on the \emph{next} iteration, not within one.
\item \textbf{Click verification is weak in both directions.} A click that opens a native dialog or starts a download reads as unverified; an unrelated page mutation can make a no-op click read as verified.
\item \textbf{Approval heuristics are label-based.} A "Place order" button labelled "Continue" will not trigger the financial-action approval rule.
\item \textbf{Confidence gates approval only} -- it does not influence recovery behaviour.
\item \textbf{Key codes are best-effort} for punctuation; letters and digits are correct for a US layout. Non-US layouts and IME input are not modelled.
\item \textbf{Screenshots are uncapped in size} and are not yet fed to the planner -- multimodal/vision planning is deliberately out of scope for now.
\item \textbf{Browser memory excludes cookies, auth state, and downloads} -- those live in the Electron session where Chromium already manages them; duplicating them would add a weaker second copy of credentials.
\item \textbf{\texttt{terminal} and \texttt{email} tools are deliberately not registered.} The registry supports the category, but handing shell execution or outbound mail to an agent whose input includes attacker-controlled page text converts a prompt injection into remote code execution or a spam relay.
\end{itemize}
